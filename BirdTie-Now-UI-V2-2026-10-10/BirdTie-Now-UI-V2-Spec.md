## 0. 必须先看的一页决策

| 范围 | 本轮确定的规则 | 禁止的“修复” |
|---|---|---|
| 城市选择 | 只选择要探索的城市/地理目的地 | 继续混入线上范围、公开范围声明、登录后才可选城市 |
| 底部主面板 | 手机竖屏左右贴边、底部贴底，外边距全为 0 | 把单主面板做成四角圆角的悬浮卡片 |
| 文字 | 一套语义字体 token、正常正文、紧凑但可读的层级 | 每个组件独立设字号；用缩小全部文字掩盖结构冗余 |
| 地图 | 保持真实且获准展示的位置；按缩放/类型/碰撞渐进表达 | 全城内容统一落在城市中心或一个不可分解的数字 pin |
| 地址问答 | 用户原问题保留一次；回答主体为一张完整 PlaceCard | 地址正文、来源条、全部来源、地点来源多次重复 |
| 来源 | 本次地点回答一个来源入口，打开可查看全部相关出处 | 为减少 UI 而删掉证据、伪造来源或隐藏冲突 |
| 操作 | 卡片点击联动地图；导航为主；更多内含分享/收藏等 | 五个同权重动作铺成两行；按钮无效但表现为已成功 |

本规范优先于旧规范中的冲突或模糊表达；未冲突的单地图、单 Composer、单终态、键盘单所有者、权限及真实证据要求继续有效。

### 0.1 对前一版的明确补丁

1. “一个主面板”补充为“**一个全宽贴底主面板**”。`margin.left/right/bottom = 0`；仅顶部圆角。输入框的内部左右 16 不等于面板外边距 16。
2. 地址类实体回答例外于普通 prose：有充分、无冲突的结构化卡片时，卡片本身就是回答，不再额外复述同一地址。
3. 城市选择与线上检索/公开范围彻底解耦；不能因为底层存在 Scope 模型就把所有 scope 放进一个选择器。
4. 地图聚合只是一种局部避碰表示，不是把内容搬去新位置，不是永久对象，也不是活动与地点混合计数后贴在市中心。
5. 无内容时不展示空的聊天高度占位；已有内容允许自然短展开，不强制大半屏。用户主动展开的阅读状态可以保留。

## 2. 城市选择器：只回答“你要探索哪里”

### 2.1 为什么现有“线上范围”不应在这里

按现有文案与旧需求语境，线上范围意在表示不依赖地理城市的在线活动/远程连接查询，范围声明则可能影响用户可发现性。这两者都不同于浏览地图目的地。具体执行链仍由 Codex 核验；不得对用户声称它已经能完成某种匹配。

10 月 8 日整合需求已经要求：线上与其他范围移出目的地列表；查找线上活动作为普通 Now 任务；公开范围声明放隐私与可发现性。这是落实旧决策，不是新增一套需求。[I1]

### 2.2 目标界面

- 标题：`选择城市`。
- 顶部唯一局部检索：`搜索城市`。这是城市选择器内的查找控件，不是另一个常驻 Now 对话入口。
- 城市列表：主行城市名称，副行国家/地区；当前项显示选中标记。城市缩略图已有可复用时可保留，否则统一占位或直接文字行，不为装饰扩建媒体系统。
- 有真实历史时展示“最近”；没有历史不展示空分组。可用目录项按实际数据呈现，不硬编码一批看起来可用的城市。
- 选中立即返回原 Now 地图并更新探索上下文；不要求额外确认表单。
- 删除本面板的“线上与其他范围”“登录后可选择本人声明的线上范围”“查找线上活动与伙伴”。
- “选择目的地不代表实时位置”的长说明不再常驻抢占首屏。首次确需解释时使用一句短说明或信息入口：`仅切换探索城市，不改变你的定位。`
- 没有登录、拒绝定位，仍可搜索并切换本来允许公开浏览的目的地。需账号的收藏/好友分享在具体动作处处理，完成后恢复对象与草稿。
- 真正只有试点城市可用时，明确目录限制；不可用底图、地点数据尚少、活动为零必须分开，不把“没有平台活动”等同于“城市不可选”。

### 2.3 状态边界（逻辑契约，映射现有代码，禁止无故重建全库）

| 状态 | 含义 | 选择城市时是否修改 |
|---|---|---|
| deviceLocation / permission | 实际定位及授权 | 否 |
| exploreDestination / camera | 地图浏览目的地与相机上下文 | 是 |
| queryScope | 本次查询明确的地域/视口与条件 | 在新操作明确使用该城市时更新，旧回答仍保留原范围 |
| discoverability / declaredScope | 他人能如何发现用户的隐私范围 | 否 |
| onlineTaskFilter | 特定线上活动请求的非地理过滤 | 否 |

切换城市不能发布用户位置、加入社群、扩大公开范围或用新城市中心冒充导航起点。后台定位刷新不得覆盖用户明确选择的城市。旧查询异步响应不得覆盖新城市的活跃地图图层。

城市选择器为临时模态选择：显示时底层主面板不可交互，不叠显两个独立的可操作拖拽面板。返回恢复原输入、会话与面板状态；没有选择不能产生城市切换。

## 3. 主面板：外边缘贴屏，内部内容留白

### 3.1 手机竖屏几何基线

| Token / 项 | 基线 |
|---|---|
| mainSheet.marginLeft / Right / Bottom | 0 / 0 / 0 |
| mainSheet.cornerTop | 24 |
| mainSheet.cornerBottom | 0 |
| contentInsetHorizontal | 16 |
| composerInsetHorizontal | 16（相对面板边缘，仅计算一次） |
| composerMinHeight | 56，文字缩放及多行时可增长 |
| compactSheet | 按实际输入区与内边距测量，不设置大块占位高度 |
| handle（确有可展开内容时） | 约 32×4，独立触控/可访问入口不只依赖细线拖拽 |
| source / more / top controls hit area | 至少 48×48 logical pixels；视觉图标可以小 |

这些是本轮设计基线，不是测量用户截图所得的设备 dp；执行前记录设备逻辑尺寸、DPR 与系统文字缩放。横屏、平板、桌面另用现有适配，不强迫大屏对话占整个地图宽度。

最关键的可验证关系：

```text
mainSheet.left == viewport.left
mainSheet.right == viewport.right
无键盘：mainSheet.background.bottom == viewport.bottom
有键盘：mainSheet.background.bottom == keyboard.top（在唯一 inset 所有者的坐标系内）
composer.left == mainSheet.left + 16
composer.right == mainSheet.right - 16
```

**底部安全区不是一条露出地图的缝。** 面板背景覆盖到屏幕下缘；可交互内容在内部避开系统手势区。不要把 SafeArea 放在整个带背景面板之外后，又在底部增加 margin。[R3]

### 3.2 状态与高度

- `compact`：无会话时仅显示输入入口及必要内边距；若拖动没有内容可展示，不显示误导性的拖拽柄。输入框上下各约 8–12 基线间距，不保留截图中宽大的空白头部。
- `shortResult`：由同一面板展开到自然内容高度；简单地址卡不自动变成占屏 75% 的高卡片。正常竖屏约 35–45% 可用高度为优先上限，超出则内滚动；不是大字号/横屏硬上限。
- `expanded`：用户主动拖动或查看长内容时，同一表面向上展开；正文滚动、输入框固定在该表面底部。
- `editing`：沿用同一面板与唯一输入框。键盘变化调整内容可用高度，不新建键盘条、搜索底板或 Composer 底座。
- `modalSelection`：城市、来源等短暂选择上下文可单独模态打开，但底层 Now 面板冻结交互且正确处理焦点，关闭后恢复；这不等于恢复常驻双主面板。

结果高度采用实际测量；不要用 `Spacer` 把卡片内容撑成大面积空白，也不要按固定比例创建空聊天区域。历史上下文可恢复，但首页首次空白不需要一个可以拉开的空盒子。

### 3.3 键盘与地图保留要求

只有一个对象消费键盘遮挡。`Scaffold.resizeToAvoidBottomInset` 与手动 `viewInsets.bottom` 不得对同一区域重复生效；具体选择服从实测结构，不机械套一个开关。[R4]

地图实例和数据源保持稳定；键盘、字体重排、来源展开不得清除当前 pin、重置相机或自动发一次新的区域搜索。地图允许必要 rebuild，不等于允许 dispose/recreate 实例。应用层“收键盘”不放进地图搜索条。

## 4. 字体、文字层级与节奏

### 4.1 字体策略

本轮先统一平台系统无衬线与中英 fallback、语义 TextTheme/主题扩展，不为修复引入多个网络字体。检查实际设备 fallback，确认中英数字混排的基线、字重、字符覆盖。映射既有字体资产时保留已有许可与加载方案。

地图底图的行政区/道路标签与应用正文是不同渲染体系；不把底图字号不一当作应用 Theme 全局字体问题。底图标签密度需在实际地图样式中单独校验，优先减少与业务 pin 的冲突。

### 4.2 语义表（基准 TextScaler 下的 logical px）

| 角色 | 字号 / 行高 | 字重 | 用途 |
|---|---|---|---|
| sheetTitle | 20 / 28 | 600 | 选择城市、来源详情标题 |
| placeTitle | 18 / 26 | 600 | 地点卡名称 |
| chromeLabel | 16 / 22 | 600 | 顶部城市；必要短标签 |
| body / userMessage / composer | 16 / 24 | 400 | 回答、用户问题、输入正文 |
| address | 15 / 22 | 400 | 完整地址，允许自然换行 |
| action / listSubtitle | 14 / 20 | 500 / 400 | 导航文字、国家地区与次级说明 |
| metadata | 12 / 18 | 400 | 非关键更新时间、辅助信息 |

不是全部变成相同大小，而是同类信息始终一致；正文不满屏粗体，地址不能用 title 样式；来源不再伪装成多个大按钮。

字间距默认正常，不为中文正文增加装饰性 tracking。地点名行高固定为语义比率但容器可增长；地址不得因一行溢出而省略关键门牌或邮编。极长名称可以在紧凑态有限折叠，但一跳/展开可读完整名称，完整无障碍标签保留。

### 4.3 间距与操作尺度

基础 spacing 取 4 / 8 / 12 / 16 / 24 / 32。名称到地址 4–6，地址到操作行 12，独立回合之间 16–20。无需为单地址卡添加“地点”大副标题；类型只有帮助消歧时才出现。

小来源图标建议视觉约 18–20，但触控与语义区域维持 48×48；小图标不是小点击热区。文本及操作对比度按测试检查。[R2]

使用系统文字缩放，不能通过禁用缩放或 `FittedBox` 把所有文本压小来消除 overflow。Flutter 的 TextScaler 用于接入平台字体缩放策略，应按仓库锁定版本使用相应接口。[R1]

## 5. 地图：真实位置、层级显示、局部去拥挤

### 5.1 先诊断“18”是什么

必须沿着以下链路记录非敏感诊断：查询结果 → 规范化地点/活动关联 → 坐标解析/精度 → FeatureCollection → 显示策略 → 最终命中对象。

记录：实体 ID、placeId、对象类型、获准坐标精度、合法坐标标志、不同坐标数量、选中的 scope/zoom、实际图层 ID、是否 cluster、cluster 成员数。生产日志不要额外收集私人精确位置。

至少分别排查：

1. 客户端聚合半径过大、聚合结束层级不当、未渲染 unclustered layer。
2. 接口本身只返回城市摘要，客户端误用地点 pin 渲染。
3. 缺失地理编码统一回退 city.center、首个点或 (0,0)。
4. 多条内容实际关联同一场地，应一个场地入口带明确“活动/内容”计数。
5. Feature ID 或 annotation ID 冲突，导致不同实体覆盖在一个位置。
6. lat/lng 顺序、坐标系统或屏幕投影/缩放单位错误。

仅关闭 cluster 可能得到 18 个重叠在同一错误坐标的图标，不能作为完成证据。

### 5.2 地理数据不变量

- 数据源有准确且获准坐标的不同地点，按各自坐标展示；地图展示算法不得改写存储坐标或导航目的地。
- 没有坐标：保留结果卡，显示“位置待确认”，不能放到城市中心制造可导航 pin。
- 仅获准区域级位置：按区域语义展示，不能曝光原始精确位置；不强迫所有内容精确到门牌。
- 活动位置使用活动明确场地；多地点活动保留多个关联，线上活动不应制造地理 pin。
- 同一 Place 下多个活动/动态优先使用一个场地锚点和场地内内容列表；计数明确是几个活动/条动态，不能把一个场地的 18 条内容伪称 18 个地点。
- 地址、地点名和实体存在冲突时先消歧，不自动把 Glenhouse 改成 Greenhouse，也不使用截图地址当作事实。
- 先做权限/可见性过滤再算总数、聚合、摘要；“选中保护”只豁免显示裁剪，绝不豁免权限。

注意不能照搬两种潜在偏差：

- 既有配置包含 rating/popularity 等排序项，不应直接替代 BirdTie 的当前明确意图与经授权偏好；这轮主要复用显示策略，不另造推荐排名。

### 5.4 BirdTie 目标显示策略

采用两层：**环境探索层**控制一般密度；**当前任务/选中层**保护用户明确要看的地点。它们共享实体与坐标，选中后不能视觉重复叠两个同名 pin。

| 视野 | 环境探索层 | 当前任务与选中层 |
|---|---|---|
| 城市/远景 | 按真实位置分布的代表点或轻量密度表示，少标签；不能用一个全城大数字替代全部地理分布 | 单个明确查询目标保留可识别 pin；多个结果保留空间分布与可访问列表 |
| 街区 | 按类型和相关性逐步增加具体点，局部拥挤再处理，不把分散对象远距离合并 | 选中 pin、关键路线停靠点优先；标签优先保证选中 |
| 街道/近景 | 明确真实地点，普通数字聚类应展开，标签避碰 | 名称、详情和卡片联动；同坐标内容打开列表而非无穷放大 |

先核验现有地图服务的 zoom 语义、逻辑/物理像素与可见视口，再确定各类型门槛。不得把 Civu 的像素格大小直接当 Mapbox `clusterRadius`；二者不是同一含义。

Civu 配置中的参考格宽：z<10.5 为104，z<12.5 为86，z<14.5 为68，z<16 为54，其后44；这是**已读取配置的参考值，不是本轮新设且已经实测的聚合半径**。[I3]

Mapbox 的原生 cluster 有 `cluster`、`cluster_id`、`point_count`，而 `clusterMaxZoom` 有整数缩放边界行为。实际项目若用自定义聚合/其他 Flutter 地图层，检查实际实现，不能机械复制 GL JS 的 API。[R5]

### 5.5 真正碰撞如何处理

- 稀疏且在当前可见视口内可点击的多个地点：各画各的，不能因为同城、同类型或在同一结果页就聚成一个点。
- 稠密局部：先减少环境标签、使用紧凑符号，再对真正邻近对象局部聚合；聚合控件不能长得像一个可导航地点。
- 聚合点击：缩放到成员范围或在已有主面板内展开可访问的成员列表。到了高缩放仍完全同坐标时，列表消歧，不再无效放大。
- 地点群计数与活动/动态计数分开。混合摘要需要清楚类型说明，不能一个“18”要求用户猜。
- 不能用随机坐标抖动解决重叠；必要的屏幕标签位移不改变地理锚点。
- 地图 pin 视觉可以参考 Civu 的普通26、强调30、选中34逻辑直径作为起点；实际命中与重叠分辨必须单独测试，不能简单给所有密集 pin 一个互相覆盖的巨大透明 hit box。
- 缩放与相机停止后稳定更新；既有选中对象、用户手动平移意图和 pin ID 不因输入框/字体变化而丢失。

### 5.6 卡片与地图是一份状态

`PlaceCard.entityId == SelectedMapFeature.entityId`。同一活动与场地明确关联，不能卡片为 A、地图高亮 B。点击卡片主体使用原地图定位该对象，并在必要时收短主面板；不再默认开一个新地图页。

程序性聚焦应考虑面板遮挡、顶部工具与安全区，目标位于可见地图内。仅在新明确查询/选择/导航意图时聚焦，刷新来源元数据不抢走用户相机。

## 6. 地址问答：一张卡就是回答

### 6.1 信息结构

```text
用户原问题（保留一次）

┌ 地点回答：PlaceCard ─────────────────────┐
│ 地点名称                       [来源图标] │
│ 门牌与街道                               │
│ 城市、邮编、国家（按实际地址格式）          │
│                                         │
│ [导航]                            [更多] │
└─────────────────────────────────────────┘
```

这是组件内容契约，不是高保真原型，不含已核实的实际地点地址。

卡片主体点击可聚焦地图，因此默认不再单列“地图查看”。来源图标固定一个入口，更多菜单包含分享给好友、收藏/取消收藏、复制地址等**已支持**动作。用户能力不被删除，只减少常驻动作数量。若后续测试证明收藏需高频直达，再将其升为紧凑独立按钮，不在本轮默认扩大动作行。

### 6.2 必须删除的本回合冗余

对“某地点的地址是什么”且一个已消歧可靠实体：不再同时渲染地址复述正文、`来源1`、来源域名 pill、`全部来源1`、地点块内第二次“来源”。只保留 PlaceCard 内一个出处入口。

用户原问题不是无意义重复，应该在历史中保留。删除的是 Agent 对同一个事实的多次复述，不是用户的会话记录。

不是所有回复都只能是卡片：复杂问答可有不重复的解释；无坐标、地址冲突或多候选必须保留相应不确定性信息。无法生成可信实体时回退真实说明，不能为了凑卡片捏造 POI。

### 6.3 Renderer 与数据契约（逻辑模型，不强制重命名后端）

```text
Turn
  id / revision / queryScopeSnapshot
  userMessage
  answerKind: place_fact | place_candidates | explanation | no_result | error
  entityRefs
  optionalNonRedundantExplanation
  provenanceRefs
  status

PlacePresentation
  entityId / canonicalPlaceId（如已有）
  displayName
  formattedAddress / structuredAddress
  location: accurate | approximate | unknown
  coordinates（仅准确且获准时用于精确落点）
  provenanceRefs（字段证据可追溯）
  actions（按能力、权限与位置状态计算）
```

由结构化 answerKind 和 entityRef 决定展示，不靠正则删模型句子或把所有含地址的 prose 强行隐藏。流式返回可先显示紧凑 loading，同一回合以稳定 ID 更新为卡片；不得追加一份永久正文后再追加一张同义卡片。

### 6.4 来源去重，而非删证据

- 一个地点回答：一个来源入口；点开列出真实来源名称、网页标题/URL、所支持字段、获取时间/已知更新时间。只有一个来源也无需添加第二个直接域名按钮。
- 去重使用已有稳定 source ID 或保守规范化 URL；不要仅按域名去重，也不能删除会改变目标文档的 query 参数。
- 多个来源或相互矛盾的地址：保持不同证据及冲突提示，必要时让用户选择候选；不能藏入图标后对正文假装确定。
- 没有实际来源，不画一个暗示已核实的徽章。来源打不开时真实反馈，不能称已验证。
- 来源图标语义名称例如“查看此地点的信息来源”，不是装饰性的网络地球图标；读屏可访问。
- 数据供应商在具体字段/展示上强制要求的署名仍按实际合同保留。卡片出处入口整合不替代底图 Mapbox 等强制归属标识。

### 6.5 操作的真实效果

- 导航：使用确认的目的地坐标/地址；起点由定位授权或导航服务按用户选择处理，绝不用 Aberdeen 默认城市当用户起点。位置待确认时不显示已可精确导航的假按钮。
- 地图联动：同一地图、同一对象、可见区域内高亮；无坐标不伪造。
- 收藏：已有授权与持久化路径后才反馈成功；访客登录成功恢复对象。
- 分享给好友：读取现有好友/聊天授权流程，仅用户明确操作才发送；不自动把整个私人会话或原始来源抓取内容外发。
- 更多菜单不列没有实现且点击无效果的操作。必要的能力缺口单列 BLOCKED，不伪装“已分享”。

## 8. 验收矩阵与硬性否决项

详见 `TASKS.md` 中回归矩阵，最低要求：

- 360×800、390×844、430×932 logical px；实际截图对应机型；系统 TextScaler 常规、大号（如1.3）与接近2.0；横屏或极窄窗口。
- compact、地址短结果、展开历史、IME 开/合、城市选择、来源打开、更多操作、长名称/长地址。
- 地图稀疏18个不同坐标、局部密集、同场地多活动、未知坐标、跨城市、受限可见性、选中对象、异步过期响应。
- 点位与卡片是真实数据联动，不是静态 pin；测试夹具显式标识且不得进入生产公共地图。
- 真机至少连续录制：选择城市 → 查询一个地点 → 卡片点击定位 → 来源打开返回 → 输入键盘开合 → 缩放和选中 pin。自动化通过不能冒充这段真实运行验证。

否决项：主面板左右/底部露地图缝；一次地址事实出现多份同义正文/多个出处入口；用市中心补未知坐标；地图全城结果稳定压成一个不可分解的地点 pin；字体缩放被强制关闭；空按钮伪反馈成功；权限外数据进入聚合计数。
