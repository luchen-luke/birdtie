## 1 结论与使用方式

这一轮要补齐的是交互质量：让用户按下有反馈、移动有连续性、取消有结果、输入有引导、操作有边界，且地图、卡片与输入状态不会互相破坏。采用“审计现状 → 打通一张地点卡的完整链路 → 验证 → 提炼复用 → 逐步推广”的顺序。

这份文件是对已有 AGE / AIR 工作包和 UIUX 规则的补充。它没有检查当前主仓库，也不证明现有任务已经实现或尚未实现。不要据此重做 AIR 架构、改写全应用，或把以下提案编号直接当作现有队列编号。

把文件交给当前 Codex，在它正在做的任务到达自然检查点后接续。当前任务运行期间，不要求中断，不在同一批文件上启动第二个写入者。先检查现有工作、已有规则和真实缺口，再决定哪些补充进入队列。

完成这一轮的判断依据是可复现的行为、测试和设备证据，而不是“看起来更像 Apple”、增加了多少动画、写了多少规则或通过了一张静态截图。

## 5 第一条垂直链路

第一批只选择现有的“一个地点 pin → 地点卡 → 统一输入中的查询或草稿”链路。地点卡组件的实际名称、路由和状态持有者由审计确定，不预先创造 `LocationCard` 文件或新业务模型。

### 5.1 最小演示脚本

1. 打开 Now，记录地图相机状态，选中一个实际地点 pin
2. 展开地点卡，能读完整地点信息，主操作清楚
3. 对主操作按下、移出、取消，再正常点击；取消不产生业务动作
4. 若卡片原本支持拖拽，拖到一半反向，松手回弹期间重新抓住，再关闭；若原本不支持，不为了演示新增复杂拖拽
5. 聚焦统一输入，弹出键盘，输入文字，再关闭键盘；pin、选择、相机与草稿仍保持合理状态
6. 移动和缩放地图，当前选择仍可解释，界面不因旧异步回调跳回去
7. 进行一个只读查询，结果说明恰到好处；再准备一个已有能力支持的可编辑草稿
8. 取消、返回、重进，验证草稿恢复或清除的明确约定。外部动作先在 mock / 测试环境验证，不向真实用户发送

- 这条链路中所有 P0 行为缺口均已修复并验证，或有明确阻塞且没有被标为完成

- 地图选择、键盘、卡片手势和异步状态有回归测试；地图平台视图不能自动验证的部分有真机检查
- 有修复前后同场景录屏、关键截图、测试日志和性能基线比较
- 没有新增未经授权的写入、重复提交、主导航变化或大量无关改动

先通过这道门，再推广到其他卡片和面板。若基础正确性仍失败，不用视觉润色掩盖，也不提前全局替换组件。

## 6 交互行为契约

### 6.1 按压反馈与取消

- 可交互控件区分 normal、pressed、focused、disabled、loading 及必要的 error 状态。pressed 是视觉反馈，不触发提交。
- 用户完成有效点击或键盘激活后才执行一次语义动作。拖出取消、手势被其他识别器接管、系统取消、失焦或组件销毁时，清除按压态，不遗留缩放或高亮。
- 长按、点击和拖拽不能重复触发同一动作。测试快点、连续点、按住移出、系统返回、切换前后台和 dispose 中断。
- 等待外部写入时可防止重复提交，但不能把整个界面锁死。返回或关闭能退出 UI；是否能取消已发出的请求需真实说明。
- 触控区、焦点框与语义区一致；视觉变小不应让点击区不稳定。以项目支持的平台标准核验触控目标，不把 Web 的固定 px 当 Flutter 标准。

### 6.2 动画连续与手势仲裁

- 记录当前展示位置和速度；重定向从当前展示值开始，不能从旧目标值跳转。新手势接管旧动画后，旧回调不得再关闭新打开的卡片或覆盖新状态。
- 手指移动、卡片移动和内容滚动各有明确所有者。定义地图 pan / pinch、卡片拖动、卡片内部滚动、边缘 sidebar / Inbox 手势、系统返回手势之间的优先级和取消路径。
- 手势意图未确认前，不错误吞掉地图操作；卡片内部列表未到边界时，不把普通滚动当作整卡关闭。遮罩和浮层不能让点击穿透到地图。
- 允许动效途中再次关闭、展开或反向操作。业务提交的不可重复约束与视觉动画可打断是两件事。
- 弹簧、阻尼和速度单位按当前 Flutter API 与具体交互验证。不要手抄 Web 归一化公式；零距离、极低速度、越界、尺寸变化、dispose 都有明确处理。
- 优先沿用仓库或 Flutter 已验证的手势组件。需要自定义时说明为何现有能力不足，限制自定义识别器的范围。[Flutter 手势机制](https://docs.flutter.dev/ui/interactivity/gestures)

实现可评估 `AnimationController` 与 `SpringSimulation`，但是否需要及如何组合由当前代码决定。它们提供控制和物理模拟能力，不自动保证任意卡片的可中断性，必须测试状态接管和回调生命周期。[AnimationController](https://api.flutter.dev/flutter/animation/AnimationController-class.html) · [SpringSimulation](https://api.flutter.dev/flutter/physics/SpringSimulation-class.html)

### 6.3 地图身份与相机稳定

- marker、选中地点和卡片必须引用稳定的业务身份。不要用列表索引、每次 build 的随机 key 或瞬时排序作为身份。
- 先确认实际地图 SDK 的 marker diff、平台视图生命周期和聚合规则，再定位重建、闪烁或消失的原因；不能一开始就断言是 `setState` 或插件 bug。
- 区分“对象仍选中”“对象暂时在视口外”“聚合层级变化”“筛选已排除”“数据被删除或权限失效”。卡片可保留所选对象，并提供明确的重新定位入口；不要伪造一个永远悬浮在屏幕内的 pin。
- 相机只在明确意图下改变，例如用户定位或点击重新定位。输入内容变化、键盘开合、普通卡片重建不得无条件重置相机。
- 明确地图 viewport、camera target、可见中心及 padding 的区别。键盘可能改变可视区域；允许有理由的适配，但不得产生重复补偿、无来源位移或往返抖动。
- 若新布局必须平移相机保障目标可见，使用一次明确的布局策略，保留用户随后手动操作的优先级，不在每个键盘 inset 帧重新发起相机动画。
- 取消或忽略过期的查询、相机动画完成回调和选点结果。新用户意图不能被旧异步结果覆盖。
- marker 统一正常、选中、不可用及必要聚合状态的语义；图标、颜色、描边和层级一致，不能仅靠颜色区分。

Flutter 的 `viewInsets` 表示被系统 UI 完全遮挡的区域，典型用途包括键盘遮挡。需要结合实际 Scaffold、SafeArea、地图 SDK padding 与窗口变化测试，避免多层重复处理。[viewInsets API](https://api.flutter.dev/flutter/widgets/MediaQueryData/viewInsets.html)

### 6.4 地点卡与覆盖层

- 长标题允许自然换行，并给完整内容稳定的查看方式。摘要截断仅用于合适的概览位置；不能让省略号成为唯一可获得的信息，也不能用强制缩小字体掩盖溢出。
- 标题、辅助信息、状态与主操作有清晰优先级。标签采用换行、分组或可展开摘要，具体方案根据真实内容决定，不设“标签最多三个”的脆弱规则。
- 关闭、返回和主操作在窄屏、键盘开启、横屏及放大字体时仍可达。必要时让内容区域滚动，不把关键控件挤到视口外。
- 在繁忙地图、浅色地图、深色地图及错误背景上实测文字和控件对比度。半透明与模糊只在读得清且性能允许时使用；提供不依赖模糊的实色退路。
- 模态层有符合用途的遮罩、焦点限制和返回路径；非模态侧栏不假装阻断整个应用。关闭之后恢复到合理的触发点或后继目标。
- 保留 Now 的地图主体和左右面板关系，避免为视觉风格叠多层玻璃、遮罩、阴影或运动。

### 6.5 可访问性与输入方式

- 根据项目目标平台验证文本缩放，包括系统最大可用设置；不全局关闭文字缩放。普通、长中文、长英文、混排、emoji 和缺失字段都有测试样本。
- 可操作区域具有语义名称、角色、选中 / 展开 / 忙碌状态和必要提示。避免 marker、卡片和装饰图重复播报同一内容。
- 验证 TalkBack / VoiceOver 的阅读顺序、焦点迁移、模态关闭和错误宣布。地图同时提供可访问的地点详情或等价入口，不要求读屏用户完成精确拖拽。
- 键盘路径覆盖 Tab / Shift+Tab、Enter / Space、Escape 或平台返回、可见焦点和关闭后恢复。仅在支持桌面或硬件键盘的平台纳入对应承诺。
- 输入法组合文本尚未确认时，不把 Enter 错当发送；多行输入的换行与发送按当前产品约定一致处理。
- 减少动态效果模式下保留状态反馈，但使用温和或即时过渡，移除非必要弹跳与大幅移动。检查 `MediaQueryData.disableAnimations` 及项目实际适配，不假定它覆盖所有系统无障碍信号。
- 无障碍降级不能让状态变化完全没有提示，不能降低外部写入确认要求。[Flutter 无障碍](https://docs.flutter.dev/ui/accessibility) · [disableAnimations API](https://api.flutter.dev/flutter/widgets/MediaQueryData/disableAnimations.html)

## 7 统一输入与草稿执行模型

本节描述必须可观测、可测试的行为，不要求新建一套 AIR 状态管理。先映射现有状态、事件和接口，只补缺失转换。以下名称是概念名，不是必须采用的代码枚举。

### 7.1 状态转换

| 概念状态 | 用户看到什么 | 可做什么及退出条件 |
| --- | --- | --- |
| 空闲与编辑 | 当前输入、上下文入口、可用直接控件 | 编辑、清空、选择地点；不自动创建外部对象 |
| 理解或读取中 | 即时接收反馈和真实的等待状态 | 可修改新输入或取消等待；旧结果不得覆盖新意图 |
| 需要澄清 | 仅询问影响执行的 1–2 个必要问题 | 选择结构化选项或输入回答；保留已有信息 |
| 答案或结果就绪 | 足够的简短说明和相关结果 | 简单查询到此结束；不强迫先进行额外聊天 |
| 可编辑草稿 | 已知字段、来源、缺失项、影响范围 | 直接修改、补充或取消；尚未产生外部动作 |
| 等待明确确认 | 最终版本及将产生的具体影响 | 确认该版本或返回编辑；版本变化使旧确认失效 |
| 执行中 | 单次操作进度或等待信息 | 防重复提交；关闭 UI 不谎称已撤销服务器动作 |
| 成功 | 已核实的结果及对象引用 | 查看、后续编辑或确有能力的撤销 |
| 失败且确定未执行 | 原因及安全的恢复入口 | 满足前提时重试；保留草稿 |
| 结果未知 | 明确说明尚未确认是否完成 | 查询原操作状态或人工核实；不能自动另发一次 |
| 草稿过期或权限变化 | 哪些字段、权限或版本已变化 | 刷新、重新校验并重新确认必要差异 |

不同功能可不经过全部状态。只读搜索不必进入确认；需要草稿的外部动作不能从“理解中”直接显示成功。

### 7.2 Agent 与直接控件的分工

- 优先利用当前地点、当前会话以及用户已授权的信息，显示关键来源和可修改位置。来源不确定时标明，不默默补全。
- “附近有什么”可直接展示结果，并说明检索范围；“帮我约活动”应先准备已有能力支持的草稿，再问缺失的关键条件。
- 涉及时间、人数、地点等字段时，允许 picker、选择列表和字段编辑；自然语言输入与这些控件更新同一份草稿。
- 不为了增加会话感添加假思考延时、逐字动画、无信息量寒暄或重复确认。
- 错误提示说清用户能做什么。不要把权限失效、无搜索结果和网络超时都变成“换个说法再试试”。

### 7.3 权限与确认

对每个真实动作建立简短能力表：读取哪些数据、写到哪里、谁会收到、是否产生费用或承诺、需要何种确认、是否可撤销。沿用已有服务端授权，不能只靠前端隐藏按钮保证权限。

本轮建议至少执行以下边界，并服从现有更严格规则：

- 只读查询和本地草稿编辑不增加无意义弹窗
- 创建、发送、加入、发布、邀请、删除或其他外部写入，需要清晰的动作意图和适当确认；涉及受众、金额、时间承诺、敏感数据或破坏性影响时，确认中明确列出
- 一个明确写着“发送给某人”且附近呈现最终内容的直接控件可以承载确认；不强制所有低风险操作再套一层通用“确定吗”弹窗
- 审批、登录、麦克风、位置或第三方访问授权不能由 Agent 静默代替用户授予
- 不在测试中发送真实邀请、创建真实活动、支付或写入生产数据；使用现有 mock、测试账号和隔离环境

### 7.4 草稿版本与安全重试

- 每次编辑形成可识别的草稿版本。确认绑定当前内容、目标、权限和版本；变更受众、地点、时间、费用或关键内容后，不复用旧确认。
- 草稿在恢复、切换账号、权限变化、服务端对象更新后重新校验。不要把旧账号或旧权限下的草稿自动提交。
- 提交前固定执行快照；执行中新增编辑属于新的未提交版本，不能悄悄改变已发送请求。
- 新输入、取消或组件销毁使旧推理与读取结果失效；已经发出的写请求则要继续按真实结果处理，不把“忽略响应”说成“操作取消”。
- 若服务端已有幂等键或操作 ID，沿用其协议。同一次已确认操作的传输重试使用同一身份；不要生成新身份制造第二个动作。
- 网络超时、连接断开或客户端重启不证明服务器没有执行。先按原操作身份查询或对账；若无法判定，显示结果未知并阻止自动重复副作用。
- 若后端缺少所需的去重或查询能力，记录具体契约缺口；这时前端只能保守阻止重试，不能宣称已保证 exactly-once，也不能擅自扩建服务架构。
- 草稿本地持久化遵循现有隐私、账号隔离和清除策略。不要顺手保存敏感语音、精确位置或私密文本到分析日志。

## 8 入口与异常状态

### 8.1 加号与麦克风

`+` 必须有可理解的职责。先查当前产品定义；如果它是快捷操作入口，就列出当前已支持且上下文相关的操作。可以有羽毛球示例，但不得把所有用户意图替换成固定短语，不生成虚构活动能力。

麦克风按钮按真实能力实现：

- 已有语音能力：覆盖未授权、请求权限、录音中、停止、取消、处理中、转写可编辑、失败和设备不支持；展示可见录音状态
- 转写默认进入可编辑输入，不自动变成已发送消息或外部动作；若现有明确产品约定不同，先列出风险和证据再处理
- 尚无语音能力：隐藏不可用入口，或显示明确的不可用原因与文字输入替代，不保留一个看似可点却无反馈的装饰按钮
- 不因本轮交互修复引入未经授权的新语音供应商、权限范围、音频上传或长期保存

### 8.2 状态区别与恢复

| 情况 | 必须表达的事实 | 合适的恢复动作 | 禁止行为 |
| --- | --- | --- | --- |
| 初次加载 | 数据还未就绪 | 可取消等待或稍后重试；局部占位 | 假装为空结果或假成功 |
| 后台刷新 | 正在更新，旧数据是否仍有效 | 尽量保留可用上下文，标明过期 | 每次刷新清空地图选择和草稿 |
| 空结果 | 查询成功但没有匹配 | 调整范围或条件 | 报网络错误或捏造结果 |
| 离线 | 当前无法连接，缓存新鲜度已知或未知 | 浏览允许的缓存、编辑本地草稿 | 恢复联网后自动提交外部写入 |
| 未登录或登录过期 | 身份需要恢复 | 保留安全草稿，明确登录后续 | 无限自动跳转或静默切换身份 |
| 无权限 | 当前身份不能访问或操作 | 合理的返回或申请路径 | 当作空结果，或仅绕过前端限制 |
| 限流或服务故障 | 服务暂不可用 | 符合接口约定的只读重试或稍后再试 | 无上限重试、刷新风暴 |
| 写入失败且未执行 | 已确定没有产生副作用 | 保留草稿并允许安全重试 | 丢草稿、假装已完成 |
| 写入结果未知 | 是否产生副作用尚待核实 | 查询同一操作状态，必要时人工核实 | 新建请求身份自动再提交 |

错误页、toast 和 inline error 的职责一致：关键失败不能只短暂闪过；错误恢复后不能遗留 loading 遮罩、禁用按钮或旧错误。

### IQ-P001 安全接续与现状审计

动作：确认检查点、只读检查 Git，读取适用规则和已有任务；识别真实模块、插件、状态所有者、输入流程、测试入口和 CI。

交付：一份简洁的“已知 / 未知 / 已有实现 / 实际缺口”审计，提案到现有任务的映射，以及不会覆盖现有工作的最小修改范围。

验收：每个新增缺口都有当前证据；没有重复任务，没有改写已有 DONE，没有在活动文件上并发写入。无法访问主仓库时在此标记 BLOCKED，不建立假仓库继续。

### IQ-P002 复现与建立基线

动作：逐条复验第 2.3 节；选择真实地点和长文本样本，录制首条链路；记录地图和输入的状态转换、相机事件及现有性能；在仓库已有设计文档结构中形成适用契约。

交付：问题复现表、验证矩阵初版、首条链路测试计划和性能基线。未知根因保留为假设，并注明验证方法。

验收：环境、版本、操作步骤、期望 / 实际结果、证据位置齐全；尚未运行的测试明示 NOT_RUN。已修复项不再次拆成新实现任务。

### IQ-P003 稳定地图与键盘链路

动作：依据复现证据修复稳定 marker 身份、选中对象、相机与键盘 inset 协作，以及旧回调覆盖新选择的问题。只改第一张卡相关路径。

交付：最小修复和针对性测试；说明 pin 是真正消失、移出视口、被聚合还是被筛除，避免修错症状。

验收：键盘开合、地图移动与缩放、切换选择及返回时，没有无解释的 pin 闪烁、选择丢失或相机跳变。适配性位移有明确规则和真机证据。

### IQ-P004 完成地点卡交互质量

动作：落实按压与取消、动画接管、手势仲裁、长标题和标签布局、覆盖层可读性、焦点与语义、减少动态效果。只使用当前链路需要的能力。

交付：可运行地点卡样例、组件状态测试和关键交互录屏。

验收：取消无副作用；中断没有回跳或旧回调误关；放大字体可达；模态无点击穿透；读屏和键盘路径有证据。不能只交截图。

### IQ-P005 验证第一条垂直链路

动作：执行第 5 节完整脚本，加上离线、取消、快速切换和旧请求迟到场景；运行相关静态检查与测试。

交付：首条链路 PASS / FAIL / BLOCKED 清单、before / after 证据、改动摘要和未覆盖项。

验收：没有未解决的安全或核心正确性失败；需要真机但缺设备的项目保持 BLOCKED，不以 widget test 代替。存在阻断缺口时不进入全局推广。

### IQ-P006 提炼经过验证的复用能力

动作：在现有设计体系内提炼按压态、可中断面板行为、marker 状态、文字层级、间距、层级、表面与动效 token。先检查已有等价能力，避免新建平行体系。

交付：有限的共享组件 / token 增量、适用范围、迁移清单和组件测试。命名遵循实际仓库，不预先规定新目录。

验收：提炼前后首条链路行为不退化；没有把业务权限塞进纯视觉组件，没有用万能基类统管全部界面，没有一口气替换所有页面。

### IQ-P007 补齐输入与草稿状态

动作：把第 7 节映射到现有 AIR / 输入实现；修复仅有卡片而缺少必要解释、重复澄清、控件与草稿不同步、过期确认及请求竞争问题。

交付：实际状态转换表、动作能力与确认表、草稿版本和执行结果测试。若契约已满足，补证据而不重建架构。

验收：简单问题可直接结束；必要澄清集中且不重复；草稿可直接编辑；确认绑定最终版本；旧响应不能盖新输入；未知写入结果不会自动重做。

### IQ-P008 修复入口承诺

动作：核实并实现 `+` 的实际职责；为麦克风实现已有能力下的真实状态，或明确不可用的入口策略；验证输入法和发送规则。

交付：入口行为清单、权限和失败场景测试、录音或不可用分支的可见证据。

验收：没有固定羽毛球短语绑架用户意图，没有死按钮，没有未授权音频发送，没有转写后自动产生外部副作用。

### IQ-P009 推广到左右面板与表单

动作：按已有队列先后逐个接入已验证能力，整理标签、sidebar、Inbox 和表单的层级、密度、焦点、返回和 loading / empty / error 状态。

交付：每个迁移面板的单独变更与验收；保留地图主结构和左右面板职责。

验收：紧凑布局通过真实内容和放大字体验证；常用直接控件未被聊天取代；没有底部导航或营销 feed 回流。

### IQ-P010 完善恢复与接口边界

动作：完成第 8.2 节状态矩阵；审计写入幂等、权限及状态查询是否已有实现。只有证据表明前端无法安全完成时，提出最小后端契约变更。

交付：失败恢复测试、实际后端依赖与权限阻塞说明。如变更 Go 代码或数据库契约，补充相应测试与迁移影响，不把后端升级绑定到纯 UI 修复。

验收：离线恢复不自动提交，认证恢复不重复写，超时结果不假报失败或成功。缺少状态查询能力时保守停留结果未知。未获批准的生产操作不执行。

### IQ-P011 完整回归与实机测量

动作：在最终代码上执行第 10、11 节；后续修正后重跑受影响项，记录最终 commit 或工作树标识。

交付：测试命令与退出码、实机检查、性能 trace 和基线对照、残余问题及平台限制。

验收：没有把局部测试写成全量通过，没有用 debug 模式或模拟器数字宣称真机性能达标，没有通过降低地图功能或关闭文字缩放掩盖问题。

### IQ-P012 固化规则并分批交付

动作：将稳定契约纳入一个权威文档，添加短 AGENTS 引用与适用 CI 检查；更新实际队列状态；整理可审阅的小批次结果和发布风险。

交付：权威文档路径、AGENTS 最小 diff、自动检查入口、任务映射、验收矩阵和最终报告。

验收：规则与真实实现一致，未覆盖既有规则，未新增平行宪法；所有 DONE 都有对应证据。提交、推送、合并、部署仅在已有明确授权范围内进行。

| Flutter integration | Now → 地点卡 → 输入 → 草稿 → 确认的受控流程；返回、重新进入、断连恢复及插件允许的地图交互 | 未运行平台和未连接设备的行为 |
| 可选 golden | 关键卡片 / 面板的布局和视觉退化，使用稳定字体与固定样本 | 动画连续性、权限正确性、写入安全 |
| Go 与接口测试 | 仅实际改动的权限、幂等、版本冲突、状态查询、事务或 API 契约 | 未接触后端时虚构 Go 已测试；本地测试冒充生产验证 |

按仓库 README、任务脚本和 CI 的真实命令执行。先记录入口，不盲跑与当前模块无关的命令。下面只是常见检查形态，须在实际模块和版本支持下使用：

- 针对修改文件的 Dart format 检查，以及实际前端模块的 `flutter analyze`
- 项目定义的单测 / widget 测试命令，必要时为相关目标运行 `flutter test`
- 项目实际支持的 integration_test 入口及目标设备
- Go 确有改动时，在真实 Go module 内运行相关测试，并按项目要求决定是否运行 `go test ./...`
- 仓库既有聚合检查与 CI；无法运行时记录原因、影响和最小解阻步骤

测试不得依赖任意长的 sleep 来掩盖竞争。优先使用可控时钟、可控 futures、明确状态和稳定的测试身份；真实平台动画仍需实机验证。

### 10.2 真机人工检查

以项目实际支持的平台为范围。至少覆盖能代表该范围的真实设备；若支持 iOS 与 Android，不用一台 Android 模拟器代表两端已完成。

- 键盘连续开合、输入法组合输入、横竖屏或窗口尺寸变化
- 单指 / 双指地图交互，卡片手势与地图、滚动、系统返回竞争
- 按压取消、快速重复点击、动画中反向、返回后重进
- 长文本、系统放大字体、TalkBack / VoiceOver、硬件键盘或桌面焦点
- 减少动态效果、浅深色主题，以及可获得的高对比度设置
- 后台再回来、认证过期、断网重连、写入超时结果未知
- 当前选择移出视口、聚合层级变化、数据刷新及当前对象失效

不能获取设备时，交付已验证部分，并将相应项列为 BLOCKED；不要把“请用户有空看一下”当作已完成验证。

### 10.3 每个验收项的证据字段

每条记录至少包含：实际任务 ID 与提案 ID、平台和设备型号、OS / Flutter / 地图插件版本、构建模式、分支与 commit 或工作树标识、数据样本、复现步骤、预期和实际、结果状态、证据相对路径、日期、遗留限制。

- 自动测试：精确命令、工作目录、退出码、日志；失败和未运行必须保留
- 布局：同尺寸、同主题、同文本缩放的前后截图；视觉明显问题不能只用测试名说明
- 动态交互：同脚本录屏或事件 trace；截图不能证明没有闪烁、回跳和重复触发
- 执行安全：在 mock / 隔离测试中记录请求数、操作身份和最终结果；不要把真实用户数据写入公开日志
- 性能：采样场景、设备、模式、时长、次数、trace 与指标口径；前后口径一致

证据存放遵循仓库现有 QA 目录和隐私约定。若不存在，提议一个文档目录和本地大文件保存策略，不把录屏和敏感 trace 无节制提交到 Git。

## 11 性能测量与判定

先修状态正确性，再依据 trace 优化最有影响的瓶颈。Flutter 官方建议用合适的性能分析模式和真实设备评估；debug 模式会扭曲性能表现。[Flutter 性能分析](https://docs.flutter.dev/perf/ui-performance)

1. 在改动前记录代表性真机、刷新率、OS、Flutter / 插件版本、构建模式和地图数据量。使用 profile 模式做可比较分析，必要时用 release 模式确认体感。
2. 固定测试脚本：开 Now、选择 pin、展开卡片、反向拖动、键盘开合、输入、地图移动、左右面板开关。区分冷启动、缓存暖状态和网络等待。
3. 记录 UI / raster 帧耗时分布、jank、关键交互延迟、地图重建 / marker 更新和相关内存变化。原生地图可能存在 Flutter trace 之外的工作，按插件能力补充平台工具和录屏。
4. 根据现有性能预算和设备基线确定目标；若没有预算，在实现前登记本轮可测目标和比较方法。按刷新率分析帧预算，不把所有设备统一宣称“稳定 60fps”。
5. 同设备、同脚本重复测量，报告样本量与波动。对可重复的退化追到原因；不只报告一个最好数字或平均值。
6. 优化局限在已识别瓶颈，例如无谓重建、过量 marker 更新、昂贵模糊、主线程工作或重复相机动画。不得靠移除必要反馈、无障碍或安全状态换分。

没有设备或有效基线时，性能结论写“未验证”，并提供准确复测命令与步骤；不能在计划阶段保证具体帧率、耗时改善比例或所有机型流畅。

## 13 规则如何长期生效

### 13.1 一个权威入口

优先增补仓库现有 UIUX / interaction quality 规范的合适章节。如果没有合适的权威文档，再按仓库目录习惯创建一份交互契约；不要把本文件和新规范同时维护成两套独立宪法。

权威内容应包括：适用界面、必须保持的产品结构、按压 / 取消契约、地图 / 键盘状态边界、输入与草稿执行边界、无障碍、异常恢复、性能测量方法和验收入口。文件路径需由审计确定，不能报告一个尚未创建的路径已经落库。

在根或适用模块 AGENTS 中只增添短引用：哪些修改必须读这份规范、运行哪些实际测试、提交哪些证据。保留所有原有内容和作用域，遵守父子 AGENTS 的适用关系。

### 13.2 自动门槛与人工门槛分开

- 可以自动化：状态转换、连点去重、取消、旧响应失效、语义存在性、布局溢出、受控文本缩放、草稿确认与幂等契约
- 需要设备或人工补充：原生地图闪烁、键盘动画、复杂手势体感、真实读屏体验、最终视觉可读性和性能
- 不新增靠文本数量判断设计质量的 CI，例如“恰好两个按钮”“标签不超过三个”“必须有某句文案”；这些规则容易误伤正常产品演进
- 对 golden 变化要求行为和布局理由，不能一次接受全部新基线掩盖回归
- 沿用现有 lint、测试框架和 CI 结构；新增检查先证明稳定、有明确失效含义和可维护的数据样本

### 13.3 代码审阅清单

每次相关改动说明：影响哪条交互、是否引入外部副作用、取消与过期响应怎样处理、文字缩放与焦点是否变化、地图身份 / 相机是否变化、已运行和未运行哪些检查。

这份清单应短到会被真正使用；完整细则留在权威文档和测试，不复制到每个页面文件顶部。

长标题、长中文 / 英文 / 混排、标签和放大字体不能溢出或使操作不可达。不靠缩小字体或全局禁用文字缩放解决问题。检查浅深色和繁忙地图上的覆盖层可读性，提供不依赖模糊的退路。
验证读屏语义、焦点顺序、模态焦点限制、关闭后恢复、键盘 / 系统返回、输入法组合文字和减少动态效果。地图提供可访问详情或等价入口。
统一输入映射现有状态：编辑、理解 / 读取、必要澄清、答案、可编辑草稿、确认、执行、成功、确定失败、结果未知、过期 / 权限变化。不要另建平行 AIR 状态系统。
草稿编辑和直接控件同步；确认绑定最终版本、目标、权限与影响。关键内容变化使旧确认失效。新输入使旧读取结果失效；关闭 UI 不等于取消服务器已经执行的动作。
写入超时不能视为未执行。沿用已有幂等键 / 操作 ID 查询同一操作，未知结果禁止自动新建一次提交。缺少后端能力时如实阻塞；只有实际需要且获得相应授权才做最小后端修改。
加号遵守真实产品职责，不把所有输入写成固定羽毛球短语。麦克风若已有能力，覆盖授权、录音、取消、处理、可编辑转写、失败；若没有，明确不可用或隐藏死入口。不自动引入语音供应商，不静默上传或发送。
区分 loading、refreshing、empty、offline、auth、permission、service error 和 unknown write outcome。网络或认证恢复后不自动重做外部写入。保留符合隐私与账号隔离要求的草稿，不泄露到日志。
