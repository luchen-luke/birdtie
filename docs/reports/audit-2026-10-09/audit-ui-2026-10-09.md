# Birdtie UI / UX 验收审查 · 2026-10-09

审查方式：只读原生 Flutter 源码审查＋已有 Android 真机截图人工检查。采用 Impeccable native audit 的证据原则；本报告不是已执行双代理完整 critique，也不是新一轮真机验收。没有运行测试、构建、启动应用、修改 UI 或修改队列。

## 结论

**当前消费者可见界面未达到可验收标准。** 已有真实地图、查询、来源、公开动态和返回链路，不能抵消首屏结构、面板层级、重复空状态和导航可发现性问题。技术实现状态和视觉验收状态必须分开；DONE 不应直接解释成可发布或用户已经满意。

本轮整改优先级 P0 表示“用户已指出且阻断本轮产品验收，先于新功能处理”。不表示每一个问题都让代码完全不可运行；按通常缺陷分级，多数是 P1 重大体验问题。不得把视觉问题都归为低优先级 polish。

## 为什么已有修复还不能验收

1. **闭环能跑和界面可接受被混在同一“完成”口径中。** 既有报告证明的是某个构建、某条有限数据链路或某个状态守卫；并没有证明页面整体达到统一方案。`ui-repair-2026-10-07/REPORT.md` 自己仍标 PARTIAL。
2. **屏幕缺少整合设计，修正往往表现为继续加容器、说明或入口。** 当前源码同时维护地图 chrome、背景 Material、context lane、结果 sheet、composer 和键盘恢复入口；视觉上就会出现叠层。统一方案已经要求“唯一面板 / 唯一输入”，不能再把每个局部可运行视为整体验收。
3. **最新截图与源码没有始终对应。** APK33 构建成功不等于 APK33 的完整 UI 已经过审；旧截图只能证明当时构建，原型只能证明方向。需要保留每一条证据的版本边界，避免在变更后继续引用旧通过。
4. **开发阶段测试范围需要收紧，但不能以单元通过替代产品验收。** 日常按用户要求仅跑当前修改的单元 / widget 测试与一个受影响流程；这些布局问题无需每项全量 Flutter / Go、全量分析或重编译。只在一组布局修复完成后构建一次最终 APK，集中做上述少量截图与流程检查。性能、完整设备与发布矩阵安排独立检查点，未做记 NOT_RUN。

## 可保留的基础

- 真实 Mapbox 底图与可追踪来源链已经存在，不需要推倒地图基础。
- 当前输入框、表面 tokens、明确触区、公开内容不是实时位置的说明、权限与迟到响应守卫有可复用基础。
- Place → Moment → 作者 → 本人资料 → 返回已经有真实有界证据；后续应改善同一流程的结构与比例。
