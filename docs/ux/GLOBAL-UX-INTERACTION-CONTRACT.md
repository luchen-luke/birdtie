# Global UX Interaction Contract

Status: canonical cross-product interaction rules. Feature-specific behavior belongs in product documents such as [Now — Agent Map Workspace](../product/NOW-AGENT-MAP-WORKSPACE.md).

## Identity and projections

- Every domain entity has one stable ID for the lifetime of its projections.
- A Pin, Card, Sheet row and Conversation result are projections of the same Entity, not separately owned records.
- Selection and viewport are independent. Moving the camera does not clear the selected entity.
- Viewport state does not own or implicitly replace a ResultSet.

## State and async behavior

- State axes with separate responsibilities do not implicitly clear one another. Focus, keyboard, sheet extent, camera movement and loading are not commands to reset results or selection.
- Asynchronous search/Agent/map requests carry a current request or turn identity. Cancel or ignore stale responses so an older request cannot overwrite a newer result.
- Loading preserves stable content and the surrounding workspace. Empty states explain the absence and offer useful next steps. Errors preserve the workspace and provide a real retry path.
- Agent interactions show a natural-language response before structured results. Response content is based on actual runtime data and capabilities.
- Follow-up turns inherit the current task/conversation context, intent, filters, location/City context, time range and selection when relevant.

## Input and map

- Keyboard/focus changes may move the composer, conversation and result overlays; they must not recreate the map.
- Camera movement does not perform destructive refresh. Map search requires an explicit user action.
- A visible control must perform its labelled action. If an action is unavailable, disable or omit the control and explain the boundary; never leave a fake button.
- Voice recognition, when available, fills an editable draft and never auto-sends.

## Content and accessibility

- The default product language is Simplified Chinese (`zh-CN`). Birdtie's primary audience is Chinese-speaking international students, so navigation, actions, onboarding, status, empty/error/loading states and Agent responses must be Chinese-first. English is a secondary supported language and may be selected when a complete English localization is available; do not ship English-only primary flows under the Chinese locale or mix English UI labels into Chinese screens. Preserve proper names, user-authored text and source titles in their original language.
- New user-facing strings must be authored in Simplified Chinese and kept separate from machine identifiers so they can be localized. English is the secondary localization target; do not expose an English language choice until its user-facing flows have complete translations. API-generated Agent messages and follow-up suggestions must follow the active locale; the current default locale is Simplified Chinese.
- Date, time, number and status labels follow the active locale. Machine values, IDs, protocol fields and stable domain enums remain language-neutral in storage and APIs.
- Layouts support realistic production text lengths, wrapping and scrolling. Important names remain identifiable; expanded detail shows complete titles.
- Dynamic text scaling must not clip text or make primary actions unreachable.
- Respect device safe areas and platform text input behavior.
- Touch targets should meet platform accessibility expectations (at least 48 logical pixels on Android and 44 points on iOS where feasible).
- Preserve keyboard focus and provide visible/semantic labels for actionable controls.
- Async state changes must not steal focus from a user's active draft.

## 2 所有功能共用的十二条规则

1. **先定义用户结果。** 每个界面先写“谁要完成什么”，再决定入口、信息和控件；不得从数据库字段清单反推首屏
2. **先整理再询问。** 先检查本任务可合法复用的已确认上下文，形成可编辑草稿或真实结果，再询问会改变当前决策的缺项
3. **Now 为主入口，直接操作仍然存在。** 用户可以说需求，也可以通过详情、列表、Plans、消息、组织工作台和设置直接完成同一件事
4. **对话与结构化控件协作。** 用短对话解释和澄清，用选择控件、结果卡、预览卡和稳定详情承载状态；不得用无尽聊天替代一个可检查的任务
5. **渐进展开不隐藏关键后果。** 当前代表谁、目标对象、收件人或受众、关键内容、费用与承诺、必要时间地点，必须在相关决策和最终提交时可见
6. **少输入不能靠猜事实。** 已确认且有效的资料可以预填；推断标为建议，冲突说明来源，未知保留未知；不编造位置、身份、资格或同意
7. **用户控制真实有效。** 用户能修改、返回、取消、查看进度和找回结果；不愿使用 AI 或定位时，有相同权限范围内的普通路径
8. **所有入口使用同一领域动作。** Now、卡片和详情复用权威实体、动作契约、权限检查与状态更新；不得实现三套会给出不同结果的提交逻辑
9. **批准只对应已展示的具体版本。** 草稿、批准、提交和成功分开；内容、主体、目标、受众或关键资源版本变化后，旧批准不能执行新动作
10. **一次意图不能造成重复副作用。** 多次点击、重试、切页、重启和迟到响应都必须安全；未知结果先核实，不能盲目重发
11. **统一视觉和语言。** 优先复用项目既有 token、组件、实体名称与动作词；新页面不能自行创造一套按钮、间距、颜色和状态语义
12. **每个功能带真实验收。** 交付同时包含正常、异常、权限、移动端与可访问性证据；漂亮截图、通过 lint 或功能数量都不能代替用户完成任务


## 4 按角色和任务组织信息架构

### 4.1 页面职责必须能用一句话说清

每个现有或新增页面先记录：目标用户与工作身份、主要任务、进入路径、当前状态、主要下一步、返回去向、权限要求、空态和失败路径。这个记录附在现有功能设计或评审中，不要求再建独立系统。

| 场景或页面 | 核心职责 | 必须保留的边界 |
| --- | --- | --- |
| Now | 表达意图、组织上下文、呈现候选、继续当前任务 | 不承载全部历史数据管理，不要求先懂 Intent 或 Runtime 术语 |
| 发现列表与地图 | 浏览、比较、筛选可见供给 | 地图是空间视图；线上与跨城市任务不依赖定位 |
| 活动和其他实体详情 | 查看权威信息、状态和可用动作 | Now 中的卡片能到同一实体；最新状态不藏在聊天历史里 |
| Plans | 找回已加入、保存或正在安排的计划及变更 | 报名、候补、取消和出席不混为一个“已完成” |
| 消息 | 用户与其他人的明确会话 | 不默认进入 Agent 上下文，不把 Now 对话当人际聊天 |
| 通知 | 提示需要关注的事件，并跳到权威对象 | 已排队、已发送、已送达和已阅读分别表达 |
| 组织工作台 | 以指定组织身份管理获准资源和运营事项 | 与个人身份区分；多组织的权限、草稿和批准不能串用 |
| 个人资料与设置 | 查看和修改资料、隐私、授权及账户状态 | 隐私、退出、删除账户、屏蔽举报和帮助必须可直接找到 |

对只做浏览的访客，不先索要与浏览无关的完整资料。对普通参与者，优先呈现发现、决定和后续安排；对组织者，允许必要的批量管理、筛选和高密度工作视图。高频管理工具可以使用清晰表格或完整编辑器，不得强迫组织者逐字段聊天。

### 4.2 统一入口不等于统一成一个巨型服务

入口、理解与展示可以统一，业务职责继续分开。活动、关系、组织、消息、隐私分别通过已有 canonical domain API 和 action handler 更新状态；客户端优先复用现有 action reducer 或等价状态逻辑。不得为 Now 建立绕过领域权限的万能写接口，也不得为这次调整先引入新的状态管理框架、Agent 后端或数据库体系。

同一用户意图从 Now、结果卡或详情发起，应获得一致的资格判断、参数校验、批准要求和结果语义。入口差异只影响交互方式，不改变权限。

## 5 Now 与结构化交互的统一流程

### 5.1 默认采用六步任务流程

1. **表达目标**：用户输入一句话、选快捷任务，或从实体详情带着上下文进入
2. **整理已知信息**：系统解析本次输入，读取本任务获准使用的资料和最新领域事实，形成简短的“我的理解”或候选结果
3. **补必要缺项**：优先给出可选项和建议值；只问会改变当前结果、影响授权或阻止执行的问题
4. **查看和修改草稿**：以结构化卡片显示当前任务及关键值，允许就地改一项、展开完整编辑或保存后继续
5. **按策略确认并执行**：需要批准时展示绑定版本的动作预览；读取或已有明确授权覆盖的低风险步骤不机械重复确认
6. **确认结果并找到后续入口**：收到权威结果后显示真实状态，给出详情、Plans、会话或管理页入口；结果未知时进入核实状态

步骤可以合并或跳过已经满足的部分。例如用户原句已包含时间、方式和对象，系统不应再逐项询问一遍。一个简单的只读检索不需要额外“是否允许我搜索”的仪式。外部写动作则不能因话说得自然就省略应有授权。

### 5.2 每轮 1 至 2 个问题是交互预算

普通流程默认每轮优先询问 1–2 个最有价值的问题，而不是一次展示十几个空字段。这个目标用于减少认知负担，**不是整个任务只能有 1–2 个必填项**，也不是必须把十个问题拆成十轮聊天。

- 缺项较多时，先说明还需要哪些信息，按主题提供简洁分组或完整编辑入口，由用户选择填写方式
- 涉及安全、资格、关键时间地点、受众或费用时，缺什么就核实什么；不得为达标而猜测、隐藏或自动勾选
- 可选项有安全且符合已知偏好的默认值时可展示默认；用户能看见和改掉，默认不授予新权限
- 如果一个界面仍需大量字段，先问能否复用已知值、延后非必要字段或拆成不同任务；确属专业编辑需要则保留，并记录理由
- 衡量整个任务耗时、误解和完成率，不能只优化单轮问题数或首屏字段数

### 5.3 卡片是可检查的任务状态

活动候选卡、意图摘要、草稿预览、确认卡和结果回执必须有明确职责。卡片不是把长表单缩小塞进聊天气泡，也不能只是无法编辑的大段模型文字。

当前任务区域应让用户随时知道：正在做什么、代表谁、已采用哪些关键条件、下一步是什么、是否已对外产生效果。首屏优先一个明确主动作及必要的次动作；不为凑按钮数而隐藏修改、取消或后果说明。

长任务可以保留简短对话历史，但应有稳定的当前任务卡或任务详情，不需要向上翻几十屏才能查看最新草稿。卡片更新保留用户编辑与阅读位置；旧卡片注明已过期或仅供查看，不能继续提交另一版本。

### 5.4 多任务与短答的语义

每个意图或草稿有独立身份、工作主体、数据版本、状态和恢复入口。实现方式先复用项目现有任务模型；不能用一个全局表单对象同时承载找伙伴、建活动和组织资料编辑。

- 用户切换任务时保留各自草稿；新的草稿不覆盖另一任务未保存输入
- “是”“好的”“确认”等短答只可以绑定当前清晰选中、仍有效、用户可见的提案；多个待确认动作并存或指代不清时，先让用户选择
- 切个人、组织 A、组织 B 或账号后，旧草稿仍归原主体；不得悄悄改变所有权或携带旧批准继续提交
- 查询 A、B、C 连续发起时，迟到的 A/B 不能覆盖 C 的当前结果；历史任务可以保留自己的结果
- 任务跨页面、前后台或重启恢复后，先读取权威状态及权限；不从聊天文本推断“上次已经成功”

## 6 上下文复用与渐进展开

### 6.1 对每个字段先判断再展示

设计者应将所需信息分为以下四类，并在现有功能说明中给出少量关键例子，无需新建字段平台：

| 信息类别 | 系统应做什么 | 用户看到什么 |
| --- | --- | --- |
| 已明确提供且仍有效 | 复用当前输入或适用的已确认资料 | 可编辑的当前值，不重复要求填写 |
| 有权威来源但易变化 | 从领域服务刷新并检查权限与版本 | 当前值及必要的更新时间或状态变化 |
| 只有推断或存在冲突 | 保留来源，提出候选，必要时澄清 | “建议”“待确认”或冲突说明，不冒充事实 |
| 执行必须但尚未知 | 明确说明为何需要，提供最少输入方式 | 必要问题或相应编辑控件，不伪造默认值 |

身份、组织成员资格、资源归属、可见范围和执行权限由可信服务决定，不能从用户一句“我是管理员”或模型判断写入。用户可以纠正自己的偏好，但不能用文字绕过组织授权。

### 6.2 来源 可信程度与时效必须可解释

复用资料须在内部保留来源引用、确认或观察时间、适用范围、版本和失效条件，优先复用 AGE 和领域服务已有记录。用户需要时能展开简短来源，不要求首屏塞满技术字段。

- 将“用户已确认”“组织公布”“系统当前状态”“模型建议”区分开，不用一个模糊的可信徽章覆盖所有数据
- 相对日期、跨时区活动、过期意图和已取消活动需要明确处理；本次输入中的“周六”不能悄悄沿用过去任务的日期
- 历史城市、旅行目的地、照片定位和地图中心不代表用户当前位置；请求需要位置时使用用户指定范围或获准的当前来源，必要时询问
- 未经校准的模型分数不展示为正确概率。解释只给有依据的简短理由，不泄露原始私聊、秘密或隐藏推理
- 用户纠正、删源、撤回授权或切换上下文后，相关预填、缓存、候选和待提交动作应按现有机制失效或重新核验

### 6.3 可以展开细节 不能折叠决策依据

描述、标签、可选高级配置和次要元数据可以按需展开。作用主体、真实收件人或受众、对外可见内容、费用及承诺、关键时间地点、关键资格和无法撤回的后果，必须在相应决策节点以及最终预览中可检查。

“更多设置”不能成为隐藏公开发布、分享位置、给所有人发消息或付费条件的地方。公开受众、保存记忆和第三方数据使用不能靠默认折叠开关偷偷启用。风险内容说明应短而具体，不用大段免责文字代替明确选择。

## 7 权限 用户控制与动作生命周期

### 7.1 系统可以先做的工作

在当前任务、合法访问和授权范围内，系统可以只读检索、比对已知资料、整理候选、校验缺项、生成本地草稿和格式化展示。这是减轻用户负担的主要来源。

“自动整理”“后台完成”“用户只确认最后一步”不得被解释为默许以下动作：读取不相关私聊或私密记忆、请求未批准的数据出口、保存新的长期记忆、公开发布、发邀请或消息、报名、付款、扩大组织权限或改变可见范围。后台已发生的服务端草稿保存也应符合项目的数据保留和授权规则，不能伪装成纯本地预览。

Now 与人与人 Chat 严格分开。用户打开一段会话或在同一 App 使用聊天，不表示允许 Agent 将该会话加入上下文。检索、分析、第三方模型接收、记忆保存和公开展示分别遵循相应目的与许可，不合并成一次含糊同意；已经准确覆盖的许可则不应无意义地重复索要。

### 7.2 使用现有生命周期表达真实进度

以下是用户可理解的语义要求，映射到已有状态和契约，不要求照此另建数据库枚举：

| 状态 | 允许呈现的含义 | 不能暗示的含义 |
| --- | --- | --- |
| 草稿 | 已整理，可修改，尚未执行所预览的对外动作 | 已发布或已发送 |
| 等待确认 | 具体版本已准备好，等待适用授权 | 任意一句肯定可批准所有任务 |
| 已批准 待提交 | 已取得此版本授权，仍需执行前校验 | 执行必然成功或永不失效 |
| 处理中或已提交 | 已进入真实执行阶段，显示已知事实 | 假百分比、已收到或可保证撤回 |
| 成功 | 权威来源确认了所描述效果 | 提案生成、排队或网络请求发出就是成功 |
| 失败 | 已知此次效果未成功或确定被拒绝 | 所有失败均可安全重试 |
| 结果待核实 | 可能已经生效，正在查询或等待核实 | 可以重新创建另一笔相同动作 |
| 已取消或已过期 | 未提交步骤已停止或许可失效 | 已在途动作也必然撤回 |

批准回执不是成功回执。成功后的权威实体和状态进入详情、Plans 或相应管理页；不能只在对话里显示一句“完成了”。

### 7.3 不可变动作版本与确认绑定

复用 AIR 的 `logical_operation_id`、`action_id`、`action_digest`、批准回执和领域资源版本语义，或映射到仓库已经存在的等价实现，不建立第二套审批账本。

每次需要批准的预览必须明确对应主体、目标、受众、操作内容和关键参数，以及最新权限与资源版本。用户可以逐项编辑，编辑形成新的可审阅版本；旧版本的按钮、会话短答和批准不允许提交新版本。执行前还要重检当前角色、成员关系、屏蔽关系、资源状态与许可有效期。

任何改变执行含义的差异都必须使旧批准失效并重新展示；无影响的展示性变化如何处理，由 canonical action normalization 规则明确，不能由模型临时认定“不重要”。用户在别处修改资源或被移除组织权限后，客户端旧预览不能继续有效。

确认按钮使用具体动词，如“向所选 2 人发送邀请”“以某组织发布活动”“确认报名”；避免只写“完成”却掩盖外部动作。一个明确绑定当前预览的按钮可同时构成批准和提交入口，不为流程形式强制再加一次重复确认。

### 7.4 重试 取消与未知结果

双击、断网、响应丢失、重启和同一动作跨入口重试，必须沿用稳定逻辑操作和效果键。纯前端禁用按钮只能改善体验，不能替代服务端幂等和权限校验。

同一次逻辑操作的重试与用户明知结果后明确发起的另一次合法操作必须区分。后一种即使内容完全相同，也应获得新的逻辑操作 ID，并按本次状态和许可重新判断；不得仅凭 payload 相同永久去重，也不得为了绕过未知结果核实而自动另起操作。

- 提交前取消：不再产生新副作用；允许返回编辑或另起新意图
- 提交后请求取消：诚实显示已提交或在途状态，停止尚未执行的后续步骤；撤销若是新的业务动作，按其权限和后果单独处理
- 结果未知：查询权威状态或运行既有对账流程，展示“正在核实”；无法确认时给出明确支持路径，不盲重发，不报假失败诱导用户重复点击
- 已确认失败且可安全重试：说明可重试范围，保留非敏感输入，重试同一操作而非无意创建第二次意图
- 服务端返回过期、已满、撤权或受众变化：更新预览与下一步，不靠客户端旧数据继续提交

### 7.5 始终可达的控制入口

用户不必先对 Agent 解释原因，就能查看或修改隐私范围、管理 AI 和记忆授权、取消尚未提交的任务、退出账号、发起账户删除、屏蔽、举报和寻求帮助。破坏性或高后果动作继续保留必要的核验与后果说明。

拒绝 AI、关闭模型服务、预算耗尽或不提供定位时，同权限范围内的普通发现、详情、编辑、报名和 Plans 路径应可用；拒绝定位的用户可以选择城市、区域或线上活动。降级不得让用户重新填写已合法保留的安全输入，也不能静默扩大数据使用。

## 8 视觉系统与组件复用规则

### 8.1 先审计现有实现

在真实仓库中盘点已有主题、design tokens、页面壳、输入、选择、卡片、动作、状态、弹层、导航及可访问性实现。对每个需要的能力标记 `REUSE`、`EXTEND` 或有理由的 `NEW`，并指向代码或现有设计规范。

优先扩展一个被真实流程共同使用的组件，再让相关页面逐步使用。不得为了追求统一，先引入新 UI 框架、替换整个 Flutter 状态体系、建新后台 schema，或开展没有明确用户收益的大范围“零硬编码”重写。

### 8.2 最小组件职责

下列是职责名称，不预设实际类名和文件路径：

| 组件职责 | 必须统一的行为 |
| --- | --- |
| 输入与任务快捷项 | 输入状态、提交语义、键盘行为、清除与恢复、禁用原因 |
| 选择与条件项 | 单选或多选语义、当前值、必需性、撤销选择、读屏标签 |
| 当前任务摘要 | 工作主体、关键条件、状态、修改和取消、任务切换 |
| 实体结果卡 | 稳定实体引用、核心事实、可用动作、过期或无权状态、详情入口 |
| 动作预览与确认 | 可见参数、受众和后果、版本绑定、具体动词、拒绝与编辑 |
| 执行状态与错误 | 处理中、空、失败、权限阻断、取消、未知结果和恢复方式 |
| 实体详情与编辑 | 权威信息、生命周期、渐进展开、完整编辑、保存后的去向 |

统一 design tokens 至少覆盖语义颜色、字体层级、间距、尺寸、边界、圆角、焦点、禁用和危险状态；数值以现有系统与实际设备验证为准，不在这份规则中武断指定一套新视觉风格。确有特殊需求时先扩展语义 token 或组件变体，保留小范围有理由的例外。

### 8.3 页面密度与文案

- 同一区域只承担一个主要决策；先给用户当前需要的摘要和下一步，再展开细节
- 通过删掉重复内容、分组、合理留白和降低非必要控件的优先级减密度，不能靠缩小字体、压缩点击区或把所有东西塞进横向卡片
- 不一页同时堆满完整聊天、筛选器、地图、创建表单、设置和管理面板；按任务切换或分层展示
- 不把管理用的 JSON、内部 ID、schema 字段名或 Runtime 状态直接当普通用户文案
- 相同对象和动作使用一致名称；“保存草稿”“发布”“申请加入”“已报名”“候补”“出席”含义不能混用
- 错误说明“哪里出了问题、已发生什么、下一步能做什么”；不能所有异常都写“暂无结果”

### 8.4 移动端 键盘与辅助技术

所有主要任务必须在拟支持的真实设备、窄屏、大字体和键盘弹起时完成。关键受众、费用、时间地点和确认按钮不得被裁切、遮挡或依赖悬停；较长信息可滚动查看，但不能无提示地藏掉后果。

选择项和卡片动作为有标签、有角色、有状态的真实控件。焦点顺序符合任务顺序，错误关联到对应字段；弹层打开、关闭和返回后焦点位置合理。异步卡片更新不能抢走用户焦点，流式输出不逐 token 干扰读屏；动态状态用节制且可理解的方式通知。

适用设备提供键盘完整操作、可见焦点与正确提交行为；手机验证触控范围、单手常用路径、系统返回和前后台恢复。地图提供等价列表和地址路径，不以颜色、图标或手势作为唯一信息来源。自动检测只能补充原生辅助技术实测。

### 8.5 克制的轻磨砂表面与首条地点链路（2026-10-04）

用户明确指定 BirdTie 的表面方向为“地图清晰、控件轻透、内容稳实”。保持 Now 全屏地图、统一输入框、左侧栏与右侧 Inbox；沿用现有导航。来源计划为 [交互质量执行方案快照](../product/BirdTie-Interaction-Quality-Codex-Plan-2026-10-04.md)，原始路径与去重记录见 [本轮审计](../research/BIRDTIE-INTERACTION-QUALITY-2026-10-04-AUDIT.md)。日期快照不独立演进，不另建 IQ 需求队列。

- 先做 Now 输入框与一张真实地点详情卡的完整样板。输入框与该链路的浮动入口使用轻度半透明背景；地点正文、地址、时间、主要操作使用接近实色的表面。错误、权限、最终确认优先可读性，不能让重要信息透到复杂地图中。
- 先修 pin 闪烁、稳定 ID/选择、相机/键盘和标题溢出等正确性，再调整材质。样板通过适用行为、布局与实机门槛后，按现有任务有限推广；不批量替换全应用，不全屏玻璃化，不嵌套多层模糊，不因透明或动效降低文字对比度或触控可达性。
- 复用现有 Material 主题、语义颜色、字体与组件；缺少的表面能力只作最小 EXTEND。表面颜色、透明度、模糊、边框、阴影及实色降级在同一 token 定义中维护，页面不各自硬编码。数值先登记为候选，再按实际 BirdTie 界面验证确定；不把文档或静态效果图当已验参数。
- 支持样板的浅色/深色、大字号、必要辅助技术和低性能降级。高对比度或无法证明透明可读时使用实色；减少动态效果和受限设备采用保守效果。按实际 Flutter/平台能力读取信号，不声称所有系统存在相同的“减少透明度” API。关闭模糊仍须保留边界、焦点和状态反馈。
- 只在控件真实边界内裁剪一次所需背景效果，不把整地图或平台视图包入模糊层。拖卡、地图操作和键盘开合不重建地图、批量重发 marker 或隐式清除选择；新意图和手势优先，旧回调不得覆盖新状态。
- 同设备、同数据、同视口建立前后基线：浅色地图、深色地图、密集街区、键盘弹出与卡片拖动。保存实际构建的前后截图、交互录屏和 profile 性能 trace，记录刷新率、UI/raster 耗时、jank、交互延迟及可观测地图更新。Debug 体感不能充当 profile 结论；未知/缺失项标 NOT_RUN 或 BLOCKED，不承诺固定帧率或改善比例。

### 8.6 交互质量补充验收

沿用 UX-CHECK-01 至 16，并将本轮计划 AC-01 至 16 作为原任务的核验要求，不转成十二项独立 IQ 功能任务：

- normal/pressed/focused/disabled/loading/error 状态真实；有效释放或键盘激活才执行，拖出、系统取消、失焦和销毁清除按压态。取消无业务效果，连点、长按、拖动不重复提交。
- 已有可拖卡片从当前展示值接管，旧动画不得误关新卡片；卡片内容滚动、地图 pan/pinch、左右面板与系统返回有明确仲裁，不点击穿透。不为本来无拖拽需求的组件新建复杂手势。
- 当前选择移出视口、聚合、筛除、删除和权限失效分别解释；长中文、英文、混排、缺字段、大字号与窄屏均保持完整信息入口和主要动作可达，不缩小字体或关闭文本缩放掩盖溢出。
- 统一输入继续使用既有 AGE/AIR 和领域状态：编辑、读取、必要澄清、答案、可编辑草稿、具体版本确认、执行、已核实成功、确定失败、结果未知及过期/撤权。只读不机械确认；版本变化使旧批准失效，写入超时先查原操作，不自动生成新的副作用。
- `+` 沿用真实快捷操作，不用固定羽毛球替代意图；语音只在已有真实能力内工作，否则提供明确不可用或文字输入替代，转写默认可编辑且不自动发送。不引入供应商、音频上传或权限扩张。
- 自动测试和人工门槛分开。状态/权限/乱序/取消/布局/语义用现有测试与 CI；原生地图、键盘动画、TalkBack/VoiceOver、减少动态效果与 GPU 性能使用对应实机。未测平台明确记录，不能由另一平台、模拟器或 widget 测试推断通过。

## 9 六类任务如何应用同一规则

以下是预期交互示例，不代表这些功能已经实现、已获准启用或已经通过验收。例子中的人、组织、时间和活动均须由真实输入或授权数据提供，不把示例值当产品数据。

### 9.1 找伙伴

用户在 Now 表达“周六想找人一起打羽毛球”。系统先提取活动类型和时间表达，核实必要日期与范围；只有缺少且影响检索时才询问所在区域或线上线下方式。当前找伙伴匹配遵守已报告边界：使用双方明确填写的意图与许可，不擅自引入私聊、私密记忆或精确定位来增强匹配。

系统呈现可见候选、适配的公开理由和可选下一步。用户选择对象后，邀请内容、真实对象与自己代表的身份进入预览；不会因为“帮我找伙伴”就自动向所有候选广播。提交前重新检查对方资格、意图有效期、授权和屏蔽关系。

验收重点：已给出的日期与运动类型不重复问；无许可的人不出现；拒绝定位仍能手动选范围；邀请状态真实；撤权、屏蔽和重复点击不造成未授权或重复邀请。

### 9.2 创建活动

用户给出一段活动描述。系统从本次描述和获准组织资料中整理活动草稿；组织名、活动方式、明确时间地点等已知值可编辑预填。仍未决定的集合点、容量或必要资格留为待确认；可选图片和标签后置，不让用户先填完所有资料才能看到草稿。

当前工作身份、日期时区、地点或线上入口、受众、费用及发布后影响在预览中可见。用户可直接点某项修改，也可打开完整编辑器。发布前由现有组织/活动领域服务校验权限和内容；保存草稿不能显示为已发布。

验收重点：个人与组织 A/B 不串稿；改日期或受众后旧确认失效；字段较多时可以分组编辑而非被迫逐字段聊天；发布成功进入稳定活动详情和管理入口。

### 9.3 加入活动

用户可以在 Now 说“参加这个”，也可以在活动详情直接操作。两者指向同一活动 ID 与报名动作；“这个”有歧义时要求明确选择。系统刷新名额、资格、时间地点、费用和取消条件等相关事实。

用户做出所需决定后执行，服务端区分已报名、申请中、候补、已满或活动已取消。成功结果进入 Plans；活动后续变更以权威版本更新。报名不自动成为出席，也不自动授予活动外分享或联系权限。

验收重点：模型不可用仍能报名；重复点击只产生一次逻辑效果；超时显示待核实；活动变更后的旧预览不能按旧条件继续确认。

### 9.4 分享或发送内容

系统可以整理已选活动链接或用户授权的文字草稿。发送前明确收件人、会话或群组、内容及附带资料；同名对象必须消歧。只分享可对该接收方披露的信息，不把私人匹配理由、记忆或位置偷偷拼入消息。

用户选择收件人不代表永久扩大文件、活动或个人资料的可见范围。若分享需要改变权限，单独显示权限变化；动态受众变化后重新核验。取消、撤回、对方能否查看和消息是否送达按真实能力说明。

验收重点：Now 草稿与人与人 Chat 不串内容；预览后换收件人使旧批准失效；发送失败或结果未知不造成盲重发；私有内容的访问权限在接收时仍受服务端控制。

### 9.5 管理组织

用户在指定组织工作台直接管理，也可以从 Now 说出管理目标。系统持续显示当前组织身份，检索其有权查看的资料、活动和待办，给出可执行摘要；不为每个管理动作重新要求输入组织基本信息。

复杂批量编辑使用完整工作界面，说明将影响的资源集合和人员范围。删除、权限变更、公告、活动取消及批量外发按照各自动作的后果与授权执行。切换组织只切上下文，不继承另一组织的批准或数据。

验收重点：个人、组织 A、组织 B 的同名实体和相同自然 ID 不串用；成员资格被撤回后操作被拒绝；批量范围可检查；直接入口与 Now 的结果一致。

### 9.6 隐私与 AI 记忆

用户从设置直接看到谁能看什么、哪些资料用于 AI、哪些记忆已确认、如何纠正和撤回；也可以通过 Now 请求解释或提出修改意图。系统先显示将变更的具体范围和后果，不要求用户把隐私需求写成复杂提示词。

上传内容、允许分析、允许模型供应商接收、保存长期记忆和公开展示分别遵循原许可边界。拒绝或撤回可选许可不阻断无关核心功能。删除或撤回后，说明当前系统的失效结果、在途动作和外部保留限制，不能承诺无法证实的即时全网删除。

验收重点：设置入口始终可达；长期记忆候选可接受、编辑或拒绝；旧草稿和缓存不复活撤回数据；用户能理解当前状态而非只看见开关变色。

## 10 每个功能的开发与验收门禁

### 10.1 三个检查点

**设计前**：明确用户结果、角色、直接入口、Now 路径、已知上下文和必要缺项，查找同类组件及领域动作。对照现有任务，已满足的只补证据。

**实现中**：优先复用并做最小变更。先把一条完整任务从整理、编辑、执行到恢复做通，再将相同模式应用于受影响页面。安全、隐私和权限控制必须与功能同时交付，不能以“先把 UI 跑通”为由后补。

**交付前**：对最终版本运行适用的 lint、类型检查、单元、组件、契约及端到端测试，并取得当前构建的真实界面与设备证据。后续修改影响已验收行为时重跑相关检查；阻断项写明，未运行不能记为 PASS。

### 10.2 逐功能检查表

下列 `UX-CHECK-*` 是评审和证据定位编号，**不是新任务 ID，不导入队列，不重置已有开发状态**。每个功能只引用适用项；不适用必须说明理由，已有验收证据可直接复用。证据不足标“待核验”，不能为了文档完整填写通过。

| 编号 | 必须检查的结果 | 最小证据 |
| --- | --- | --- |
| UX-CHECK-01 | 用户任务、角色和页面职责清楚，关键入口可找到 | 一句话任务、当前流程或实际路径 |
| UX-CHECK-02 | 已给定且有效的信息被复用，没有无意义重复询问 | 完整输入与缺项输入各一个用例 |
| UX-CHECK-03 | 1–2 问题默认预算未造成隐藏必需信息或冗长聊天 | 总轮次、完整编辑路径、例外理由 |
| UX-CHECK-04 | Now、卡片和详情复用同一实体与动作语义 | 代码/契约映射及跨入口结果测试 |
| UX-CHECK-05 | 当前主体、目标、受众和关键后果可检查 | 真实预览截图与字段断言 |
| UX-CHECK-06 | 来源、建议、未知与过期有明确区分，不猜位置或资格 | 冲突、过期、未知、纠正用例 |
| UX-CHECK-07 | 草稿、批准、提交、成功、失败与结果未知区分 | 状态转换和回执断言 |
| UX-CHECK-08 | 编辑、换主体/目标/受众、撤权后旧批准不可用 | 版本绑定、短答、旧卡片负向测试 |
| UX-CHECK-09 | 重试、双击和响应丢失不造成重复副作用 | 幂等与未知结果对账测试 |
| UX-CHECK-10 | 多任务、多组织、账号切换与迟到响应不串状态 | A/B/C 乱序及 Personal/Org A/Org B 隔离测试 |
| UX-CHECK-11 | 拒绝 AI/定位与模型不可用时普通路径有效 | 无 AI、无定位及权限拒绝端到端证据 |
| UX-CHECK-12 | 退出、返回、取消、前后台和重启后可正确恢复 | 中断点、持久状态及恢复结果 |
| UX-CHECK-13 | 使用现有组件、tokens、名称和状态语义 | REUSE/EXTEND/NEW 映射及定向视觉审查 |
| UX-CHECK-14 | 小屏、大字体、键盘和读屏下能检查与完成任务 | 设备/尺寸、辅助技术操作和问题记录 |
| UX-CHECK-15 | 用户无需讲解即可完成、修改、找回结果或安全退出 | 当前版本可用性观察，区分独立完成与经提示完成 |
| UX-CHECK-16 | 埋点不默认保存聊天、位置、媒体、记忆或模型输入 | 事件字段审核、访问和保留策略引用 |

### 10.3 必须包含的联合回归

首次接入以及相关共享组件变化后，优先复用现有 E2E 覆盖以下场景：

1. 一句话已含多个字段，系统正确整理，不重复询问；用户纠正一项时其他有效输入保留
2. 拒绝 AI 和定位，仍能普通找活动、查看详情并找到 Plans；线上任务不被地图阻断
3. 组织 A 的发布草稿切换到个人或组织 B，数据、权限和旧批准不串用
4. 预览后修改日期、地点、费用或受众，旧卡片和旧短答不能执行新草稿
5. 连续查询 A、B、C，晚到响应不覆盖最新任务；两个待确认任务不会共同消费一句“好的”
6. 提交后响应丢失，系统显示待核实、恢复权威状态，不造成重复邀请、报名或发布
7. 大字体、读屏和键盘下，用户能检查完整后果、修改字段并取消；焦点不被异步更新抢走
8. 任务完成后离开 Now，再进入详情、Plans 或组织工作台，可以看到同一权威结果

真实对外写尚未获准启用时，这些写入场景在沙箱或合成测试中验证，真实环境门禁保持未通过。AIR P0 仍限于既定文字记忆候选、只读活动查询和沙箱写链验证，不能借 UI 调整提前打开自动发消息、报名或 A2A。

### 10.4 视觉与可用性证据的质量

视觉证据必须来自实际 BirdTie 构建，记录 commit 或构建版本、平台、尺寸、主题、账户角色和场景；不得拿 Codex 进度截图、概念稿或孤立组件截图代表完整产品验收。截图应遮盖不必要个人资料。

定向视觉回归用于发现漂移，差异应人工检查原因，不能批量更新 golden 让失败消失。截图通过不证明交互可用；还应让未被告知按钮位置的目标用户完成有前提条件的实际任务，记录卡点、误解、修改和恢复。小样本用于发现问题，不宣称证明全体消费者满意。

任何越权、隐私泄漏、假成功、重复外部效果、错误主体提交或无法操作的关键可访问性问题，必须阻止相应功能启用；不能被平均完成率抵消。纯视觉例外和非关键优化可以记录理由、范围与后续复核方式，不为形式统一无限扩大当前任务。

## 11 用最少指标确认体验确实变好

先建立当前流程基线，再比较同一任务、相似前提和明确版本。没有基线时不随意宣布“成功率必须达到 95%”或“少两个字段就是改进”。

优先关注：独立任务完成率、开始到权威结果的总时间、询问轮次、重复填写次数、草稿纠正次数、返回和放弃位置、恢复成功、错误确认及重复副作用。区分用户主动输入、系统建议被接受和用户纠正；区分一次逻辑操作与多次技术重试。

事件只保留必要的事件类型、构建版本、流程步骤、结果码、耗时、数量和隐私安全的关联引用。优先复用现有观测框架；不默认采集聊天正文、提示词、具体选项值、精确位置、原始媒体、私人记忆、收件人清单或模型输入来分析“少输入”。如确有研究需要，另行明确目的、最小数据、许可、保留时间和访问范围。

指标按功能、入口和必要设备类型解释，不据此建立敏感个人画像。用户观察中的原话或录屏单独取得适用许可并脱敏；普通产品埋点不得顺便录入。不能用减少点击或提高确认率来合理化隐藏风险、预选公开或诱导授权。
